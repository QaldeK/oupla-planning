# Suppression de planning : soft-delete avec fenêtre de grâce de 15 jours

Un admin peut terminer la vie d'un planning depuis sa page de configuration : update du master `deleted: true` + `deletedAt` (forgé serveur, jamais dérivé de `updated` qui bouge à chaque écriture). Le planning devient strictement lecture seule (gardes 403 sur tous les writes du master, de ses occurrences et des prefs participants ; hard-delete API bloqué pour ne pas contourner le flux), mais reste consultable par tous ses participants — y compris guests — avec une alerte explicative et la date de suppression définitive. Pendant 15 jours, tout admin peut restaurer (`deleted: false`, `deletedAt` vidé) depuis la vue participant ; un cron quotidien (`planning-purge`) supprime réellement les masters soft-deletés expirés en transaction avec re-vérification (la restauration gagne la race), en cascade native (occurrences, prefs, locks, notification_events) et avec nettoyage manuel des références d'identité (`users.adminOf` JSON, `users.masterId`). Alignement ADR 0013 : les données appartiennent aux participants, pas à l'admin qui clique « supprimer » — une cascade destructive à chaud détruirait l'historique d'autrui, la fenêtre de borne le risque sans le rendre irréversible. Trade-offs assumés : emails de transition best-effort sans retry (pas de routage par `notification_events`), envoyés à tous les participants authentifiés actifs y compris ceux ayant désactivé les emails (événement terminal, non répétable) — les guests sans compte ne sont pas notifiables (aucun canal) ; pas de push pour les événements master-level (pipeline occurrence-centré) ; restauration impossible après purge (données détruites).
