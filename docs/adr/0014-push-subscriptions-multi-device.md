# Push subscriptions multi-appareils (collection `push_subscriptions`)

Le modèle précédent stockait la subscription push dans un champ JSON unique `users.push_subscription` : un seul appareil par user — la souscription d'un second écrasait silencieusement le premier. La rotation silencieuse des clés `p256dh`/`auth` par les navigateurs n'était pas gérée non plus : la subscription stockée devenait morte jusqu'à un re-souscription manuelle. Enfin, le toggle push du `NotificationModal` (préférence **par planning** sur `planning_participants.push`) appelait `unsubscribeFromPush()`, qui tuait la subscription **au niveau du navigateur** : désactiver les push du planning A coupait ceux des plannings B, C, D dont les prefs restaient `true`.

Décision : collection dédiée **`push_subscriptions`**, une row par appareil (`user` relation cascade, `endpoint`, `p256dh`, `auth`, `user_agent`, `refreshed_at`), avec **index unique sur `endpoint` seul** — tous users confondus. L'ownership d'un appareil est donc « le dernier user ayant souscrit » : sur un navigateur partagé par deux users, la souscription de B transfère la row à son compte et Alice ne reçoit plus rien pendant la session de Bob. Le transfert cross-user n'est pas exprimable en API rules (`user = @request.auth.id` verrouille précisément ce cas) → endpoint dédié `POST /api/push-subscription` (upsert idempotent par endpoint, auth obligatoire ; pattern `/api/delete-account`), complété d'un `DELETE` qui ne retire que la row de l'appelant (404 uniforme sinon). Les API rules standard restent strictement owner-only : l'endpoint push est une capability URL, aucune lecture croisée.

La rotation de clés est couverte par le **sync-on-visit** comme mécanisme primaire : `syncPushSubscription()` (`src/lib/services/push.ts`) upsert à chaque login (`authTransition.transitionToAuth()`) et à chaque démarrage déjà-authentifié (`userStore.init()`), rafraîchissant clés, `refreshed_at` et ownership. Le handler SW `pushsubscriptionchange` a été écarté : déclenchement notoirement incohérent entre navigateurs, et le service worker n'a pas accès au token PocketBase (localStorage inaccessible depuis ce contexte) — l'appel authentifié exigerait une stratégie de token dédiée sans couvrir mieux le besoin.

Sémantiques de cycle de vie explicites :

- **Logout explicite** (`logout()`, `logoutAndStayOnPlanning()`) : suppression de la row de cet appareil via `detachCurrentDeviceFromAccount()`, **sans** `sub.unsubscribe()` — la subscription navigateur reste vivante et réutilisable (cycle logout/login sans friction, cas deux-users-un-navigateur). Fire-and-forget : une row résiduelle sera nettoyée par le 410 d'un prochain envoi.
- **Expiration de token** : aucune action — l'expiration de session n'est pas un logout.
- **Retrait volontaire d'appareil** (settings) : appareil courant → `removeCurrentDevice()` (suppression row + `unsubscribe()` + flag opt-out local persistant pour empêcher toute re-souscription automatique) ; appareil distant → suppression de la row uniquement (subscription dormante inoffensive).
- **Toggle par planning** : ne touche jamais aux subscriptions — uniquement `planning_participants.push`.

Côté envoi, `sendPushNotification` boucle sur toutes les rows du user ; un 410/404 supprime **cette row uniquement**, les autres appareils restent notifiés.

Conséquences : `users.push_subscription` est conservé mais **déprécié** pendant un cycle de déploiement (un front ancien servi par le SW peut encore y écrire), puis supprimé par une migration de nettoyage ultérieure. Options futures documentées mais non implémentées (YAGNI acté) : endpoint batch côté notify-service (`subscriptions: []` pour amortir N appareils en 1 appel HTTP — l'envoi reste aujourd'hui 1 POST synchrone par appareil depuis le JSVM), et cron de purge TTL des rows stalles sur `refreshed_at`. Voir aussi [ADR-0005](0005-push-notifications-external-service.md) : le service externe d'envoi reste inchangé.
