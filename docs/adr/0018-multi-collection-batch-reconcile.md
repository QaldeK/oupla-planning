# Batch multi-collections : convergence Dexie portée par pb-sync, sans optimisme (`executeMultiCollectionBatch`)

Les écritures atomiques multi-collections (mise à jour d'un master + create/update/soft-delete de ses occurrences) passent par `executeMultiCollectionBatch(pb, operations)` (`src/lib/pb-sync/batch.ts`) : un batch PocketBase unique — atomique côté serveur, rejoué par `withRetry` — suivi d'un **reconcile** des réponses confirmées dans Dexie (`bulkPut` de chaque corps dans la table mappée par l'opération ; les deletes, sans corps, sont supprimés localement). Le module est **délibérément non optimiste** : aucune écriture locale pré-envoi, donc ni snapshots, ni rollback, ni ids générés côté client (les ids arrivent dans les réponses serveur). À l'échec, le batch PB étant atomique, rien n'a changé ni côté serveur ni en local — comportement identique à l'ancien batch inline.

Jusqu'ici deux affirmations incompatibles coexistaient : `executeBatch` (batch.ts) prétendait au multi-collections optimiste (transaction Dexie pré-envoi, snapshots, rollback) avec zéro caller, zéro test et deux bugs latents (create sans id client impossible sur une table à keyPath, reconcile indexé faux en présence de tombstone) ; et `updatePlanningWithOccurrences` (`src/lib/services/planningMutations.ts`) affirmait en commentaire que pb-sync ne prend pas en charge le batch multi-collections, tout en écrivant un batch SDK brut **sans écriture Dexie** — la convergence locale étant déléguée par omission au SSE ou à `refreshActive`. Un trou SSE laissait alors un `master.updated` périmé en Dexie, donc un `_version` (OCC) erroné au save admin suivant. La décision découle de la mission pb↔Dexie de pb-sync (ADR-0003) et de son ambition de packaging : la réconciliation des écritures n'est plus réservée au mono-collection. Règle de choix entre les deux surfaces batch : **une collection → le builder `collection.createBatch()`** (méthode d'instance, optimiste pour update/upsert/delete — les ids sont connus localement) ; **plusieurs → `executeMultiCollectionBatch`** (fonction libre, non optimiste, convergente — le nom encode le périmètre, la doc encode l'absence d'optimisme).

Alternatives rejetées : l'**optimisme complet** (écriture Dexie pré-envoi + rollback) — coût disproportionné : ids clients 15 caractères à générer, machine à snapshots/rollback à construire et tester de zéro, pour un gain d'UI d'environ une seconde sur un flux admin qui se termine par une navigation ; la **suppression pure** — elle aurait entériné une réconciliation réservée au mono-collection, incohérent avec la promesse offline-first de la lib. Conséquences : `updatePlanningWithOccurrences` consomme `executeMultiCollectionBatch` et son refetch final du master devient redondant (le corps confirmé du batch suffit) ; `batch.ts` est réécrit en version allégée et **testé** (il devient porteur) ; le commentaire contredit devient vrai ; les docs (`src/lib/pb-sync/README.md`, `.agents/doc/user_guide/pb-sync-v1.md`) décrivent le contrat réel.
